# 자유질문 상담과 제품 비교

상담자가 실제로 보는 질문과 답변을 평가한다. 같은 사실을 담아도 표현을 바꾸면 검색어, 적용하는 근거, 되물음이 달라질 수 있다. 최초 관측 문장, 비식별 재서술, 편집한 제품 예시는 출처를 구분해 로컬 평가 폴더에 보관한다. 재서술을 실제 고객의 말투로 인용하지 않는다.

## 개발 순서와 판단 기준

첫 제품 비교의 범위는 고용보험·구직급여 상담이다. 기존 서비스에서 발견한 한 사례의 오류, 볼트를 쓰면 답이 갈린 사례, 새 제품이 실제로 더 자주 정확한 답을 준다는 주장은 각각 다른 증거가 필요하다. 과거 볼트 v2와 대조군은 생성 지시도 달랐다.

| 순서 | 직접 확인할 것 | 다음 결정을 내릴 근거 |
| --- | --- | --- |
| 1. 실제 상담 경로 점검 | 개발용 질문 한 건을 서버에 보내 구독 GPT의 첫 응답을 받는다. 볼트 유무 양쪽에 전달한 입력과 출력, 사용한 근거, 소요 시간을 보존한다. | 고객이 본 결과까지 재현되면 후보 시험을 넓힌다. 호출 실패와 근거 부족으로 인한 답변 보류는 구분해 집계한다. |
| 2. 개발 문항에서 수정 | 오류마다 공식 원문, Wiki의 서술·시행본, 모델에 전달한 발췌, 고객에게 표시된 답을 차례로 대조해 처음 어긋난 위치를 찾는다. | 해당 위치를 고친 뒤 동일 질문과 조건 하나를 바꾼 인접 질문에서 전후를 비교한다. 검토 단계를 추가한 효과도 정확도·독해·대기시간으로 판단한다. |
| 3. 노동부 서비스와 비교 | 개발 중 받은 실응답을 보고 후보와 고객 발화를 확정한다. 새 대화에서 같은 문장을 보내 양쪽 첫 응답을 그대로 저장한다. | 답변을 가린 뒤 당시 공식 자료에 따른 정확도와 고객 독해를 별도로 채점한다. 되묻는 사례는 같은 추가 사실을 제공했을 때 최종 안내까지 이어지는지도 별도로 본다. |
| 4. 독립 표본으로 검증 | 제품 버전과 채점 기준, 노동부에 보낼 표본을 결과 열람 전에 정한다. 비교 기준을 결과에 맞춰 바꾸면 탐색 결과로 표시한다. | 같은 문항의 승·무·패, 양쪽 오답, 판단 보류, 호출 실패를 전체 건수와 함께 낸다. 잘못된 기한·금액·신청 경로가 새로 생기면 사례를 따로 검토한다. 독립 평가에 쓴 문항을 수정에 활용하면 다음 평가에는 새 표본이 필요하다. |

제품의 자체 검토는 답변 생성 과정에 속한다. 독립 채점자는 답변 출처를 가린 채 사전에 만든 공식 근거표로 양쪽을 각각 판정하고, 근거와 판정자를 기록한다. 모델만 검토한 항목은 잠정 판정으로 표시한다. 공식 자료로 해결되지 않은 쟁점은 미결로 기록하고, 법적 결론을 대외적으로 주장하려면 해당 쟁점의 전문 검토 여부를 밝힌다. 가독성은 독자가 결론·조건·다음 행동을 자기 말로 설명한 결과로 확인한다.

## 모델과 입력 정책

- **개발 후보**는 같은 고객 질문에 대한 `runs/closed-openai.jsonl`과 `runs/v2/answers-openai.jsonl`의 결론·조건·행동을 직접 대조해 고른다. `priority.md`는 마지막에 대조한다. 기존 API 355쌍은 모두 `gpt-6.2-sol`이며 당시 추론 강도는 결과에 없다.
- **새 실행**은 ChatGPT 구독 Codex의 `gpt-6.2-sol` · `medium`을 쓴다. 볼트 유무 양쪽의 답변 모델·작성 지시·검토 횟수를 맞춘다. 공식 근거가 충돌하거나 원인 분석이 온톨로지·챗봇 수정을 좌우하는 경우 GPT-6.2 Astra · `xhigh`까지 사용한다.
- **질문 편집**에서는 본인이 한 말과 전해 들은 말, 예정과 확정, 대략과 정확한 수치를 보존한다. 사건일이 없으면 미상으로 둔다. 과거 재현에 필요한 상담일은 두 서비스에 같은 문구로 표시하고, 실사용 발화는 고객이 입력한 그대로 기록한다. 같은 사례의 여러 표현은 한 건으로 센다.
- **실행 조건**이 바뀌면 새 시험으로 양쪽을 다시 측정한다. 모델·과금 경로 변경, 로컬 추론, 외부 제출 문구 확정은 먼저 결정한다. 업무 중에는 창을 띄우지 않고 한 문항씩 실행한다.

## 실행

질문 파일은 UTF-8 JSONL이며 각 행에 `id`, `as_of`, `question`이 필요하다. 아래 경로는 예시다. 실제 입력과 채점 자료는 Git에서 제외한 `docs/evaluation/` 아래에 둔다.

```sh
python -X utf8 scripts/ask.py answer "궁금한 점" --format text
python -X utf8 scripts/bench_qa.py preview docs/evaluation/inputs.jsonl docs/evaluation/trial-01 --context historical --ids case-1
python -X utf8 scripts/bench_qa.py freeze docs/evaluation/trial-01 docs/evaluation/fixed.json --ids case-1
python -X utf8 scripts/bench_qa.py message docs/evaluation/fixed.json case-1
python -X utf8 scripts/bench_qa.py blind docs/evaluation/fixed.json docs/evaluation/responses.jsonl docs/evaluation/grading-01
```

`preview`는 실제 사용자 문구, 상담일, 모델 설정, 코드·위키 지문을 기록한 뒤 양쪽 첫 응답을 개별 저장한다. 실패한 호출은 동일 설정에서 이어갈 수 있다. `--context live`는 날짜 안내를 사용자 발화에 붙이지 않는다. 실사용 표본의 `as_of`에는 실제 상담일을 넣는다. 과거 1350 게시일은 과거 재현용이다.

`freeze`에는 검토를 마친 문항 ID만 지정한다. 두 실행이 있어야 해당 문장과 응답을 내보낼 수 있다. `message`는 복사할 메시지만 출력한다. 외부 응답은 `responses.jsonl`에 `id`, `sent`(실제 보낸 전체 텍스트), `first_response`를 기록하고 수집 시각과 후속 대화는 별도로 보관한다. `blind`는 실제 입력이 일치하는 문항의 A/B 원문을 `answers.json`에, 무작위 배정표를 `key.json`에 따로 보관한다. 원문 스타일과 자기소개로 서비스를 짐작할 가능성은 남는다.

## 결과 해석

정확도는 자격·금액·기한·신청 경로 등 고객 행동을 바꾸는 쟁점별로 평가한다. 필요한 사실이 빠졌을 때는 적절한 되물음도 유효한 응답이다. 독해 평가는 독자가 답을 찾는 데 걸린 시간과 이해한 내용을 기록한다. 1350의 게시 답변과 과거 자동 판정은 정답표에서 제외한다.

차이가 큰 개발 후보에서 얻은 승패는 그 사례에 한해 보고한다. 독립 표본은 두 모델의 답을 보기 전에 정한 범위·방식으로 고르고, 후속 게시·중복·재서술을 개발 자료와 대조한다. 노동부 서비스와의 우위를 주장하려면 해당 표본에서도 미리 정한 문항을 양쪽에 입력한다.
