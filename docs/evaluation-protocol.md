# Evaluation protocol

실제 상담 질문으로 두 가지를 확인한다.

1. 같은 모델에 vault의 근거를 제공하면 답변 품질이 나아지는가.
2. vault를 쓰는 챗봇이 고용노동부 AI 노동법 상담보다 나은 답을 주는가.

프로젝트의 목표와 평가 개요는 [README](../README.md#evaluation)에 있다.

## Dataset

이직과 구직급여에 관한 시민 질문을 1350 공개 상담 목록과 검색 색인에서 수집했다. 검색어와 검색 노출에 따라 선택된 표본이므로 전체 상담의 주제별 빈도를 추정하는 데에는 한계가 있다. [1350 공개 상담](https://1350.moel.go.kr/rtmlist.do) · [고용노동부 저작권정책](https://www.moel.go.kr/site/copyright/copyrightList.do)

| 자료 | 내용 | 보관·공개 범위 |
| --- | --- | --- |
| 수집본 | 공개 페이지 사본, 게시 질문과 답변, 출처 원장 | 비공개 원본 |
| 모델 입력 | 비식별 재서술 질문과 상담 기준일 | 문항별 이용 조건과 재식별 위험 검토 후 공개 범위 결정 |
| 분할·분류 | 개발·평가 배정, 주 점수 대상, 중복·후속 묶음 | [분할 방식](#dataset-splits)과 [채점 범위](#case-selection) 공개 |
| 실행 기록 | 조건별 모델 응답, 검색 근거, 비교 판정 | 재검증을 위해 비공개 보관 |
| 평가 보고 | 모델과 제품 버전, 평가 대상 수, 지표별 결과와 한계 | [사전 채점 기준](#scoring-criteria)에 따라 검증 후 공개 |

파일별 설명은 로컬의 `docs/evaluation/1350/README.md`에 있다. 모델 입력에서 게시 답변과 분류자의 판단을 제외한다.

## Dataset splits

development set(`dev`)은 오류를 분석하고 vault와 챗봇을 개선하는 데 쓴다. test set(`test`)은 개선을 마친 시스템을 평가하는 데 쓴다.

1. 독립 사례와 그 중복·후속 질문을 한 묶음으로 둔다.
2. 두 분류자가 공통으로 고른 조문, 공통 장·절, 한쪽이 고른 조문, 한쪽이 고른 장·절 순으로 묶음의 층을 정한다.
3. 시드 `20261123`으로 층 안의 묶음을 섞는다. 층별 목록을 이어 붙인 뒤 매 10개 묶음의 3·6·9번째를 test set에 배정한다.

배정은 고정한다. 분할 전에 이미 개선에 활용한 사례와 그 중복·후속은 독립 평가 점수에서 제외한다.

## Case selection

development set에서 같은 모델이 vault 유무에 따라 결론, 적용 조건, 필요한 사실 또는 다음 행동을 다르게 안내한 사례를 우선 검토한다. 두 답의 정오는 기준 답안으로 각각 확인한다. 두 답이 일치한 사례도 외부 서비스와 비교할 수 있도록 보관한다.

주 점수의 대상은 이직한 근로자의 급여 상담이다. 사업주의 신고·서류 제출 의무도 구직자가 자신의 권리와 절차를 확인하는 데 필요한 범위에서 다룬다. 현재 채점 범위는 질문에 붙인 고용보험법 장·절로 분류하므로, 사업주가 자기 업무를 묻는 사례까지 자동으로 구별하지는 못한다. 주 점수를 낼 때 질문의 관점도 확인한다. 자영업자·예술인·노무제공자 특례와 범위 밖 질문은 따로 집계하고 중복·후속 질문은 단독으로 채점하지 않는다.

## Model roles

| 역할 | 판단 기준 | 기록 |
| --- | --- | --- |
| 사례 분류 | 질문과 법령 목차에서 확인한 조문·장·절 | 모델과 분류자별 결과 |
| 응답 생성 | 동일한 모델 설정·질문·기준일에서 vault 사용 여부 | 조건별 응답 원문 |
| 응답 비교 | 생성 조건을 가렸을 때 두 답의 결론·안내 차이 | 원문과 분리한 비교 판정 |
| 정확성 채점 | 사람이 검토한 기준 답안 | 응답별 채점 결과 |

GPT와 Claude에서 vault의 효과를 비교할 때는 각 모델 안에서 얻은 차이를 보고한다. 현재 비교 도구는 vault 검색 단계에서 정한 조문 조회 기준일을 양쪽 응답 생성에 함께 전달한다. 같은 조회일에서 근거를 인용하는 답변 방식과 모델 자체 지식으로 답하는 방식의 차이를 측정한다.

이 비교에는 wiki의 내용, 관계를 따라가는 검색, 인용 검사의 효과가 함께 들어간다. ontology 관계의 기여만 측정하려면 같은 문서와 시행본을 사용하고 관계를 따라가는 검색만 달리한 응답 쌍이 필요하다.

검색 단계는 `scripts/ask.py retrieve "질문" --as-of YYYY-MM-DD --top 16 --compare-relations`로 비교한다. `--link`를 붙이면 두 조건이 한 번의 모델 호출로 고른 출발 노트를 공유한다. 달라지는 것은 노트 순위에 그래프를 쓰는지다. 두 조건은 같은 인용·서식 연결을 읽고 같은 개수 제한을 적용한다. 사례별로 결론에 필요한 구절이 그 시점의 공식 원문과 일치하는지 확인한다. 전달한 원문의 길이도 함께 집계한다.

2026-11 수집본의 장·절 분류는 같은 Claude 모델로 두 번 독립 수행했다. 분할 전에 수집한 응답 쌍 355건은 같은 GPT 모델로 생성했다. 이 기록은 개발 사례를 선별하는 데 쓴다. 분할 후 test set의 독립 평가 결과는 별도로 산출한다.

## Procedure

1. 같은 모델에서 vault가 있을 때와 없을 때의 답을 받는다.
2. 조건을 가린 두 답을 대조해 우선 검토할 사례를 고른다.
3. 사례별 기준 답안을 정한다.
4. 공식 원문 → wiki 서술 → 모델에 전달한 근거 → 답변 순으로 대조해 오류가 처음 생긴 곳을 고친다.
5. 원래 질문과 조건 하나만 바꾼 질문으로 수정 전후의 답을 확인한다.
6. 원래 사실을 보존한 비교 질문을 확정한다.
7. 같은 질문을 두 서비스에 입력하고 첫 응답을 그대로 저장한다. AI 노동법 상담에는 수동으로 입력한다.
8. 응답의 출처를 가리고 기준 답안으로 채점한다.

development set에서 여러 사례에 적용할 수 있는 지식 요구를 찾으면 [역량 질문](competency-questions.md)에 반영한다. 원래 상담 질문과 응답은 평가 자료에 둔다.

## Reference answers

1. 해당 규정의 적용 기준일을 확인한다. 규정에 따라 이직일이나 신청일이 기준이 된다.
2. 그 날짜에 적용되는 법령과 행정규칙을 찾는다.
3. 해당 사례의 해석을 판례·법령해석례·고용24 공식 안내와 대조한다. [출처별 인용 기준](../ontology/sources.md#raw-sources)
4. 답안에 결론과 적용 조건, 근거 조문과 시행일을 적는다. 사실이 부족하면 필요한 질문을 적는다.

1350 게시 답변을 참고할 때는 작성 주체를 확인한다. 출처에는 공개 페이지에 표시된 기관이나 부서를 적는다. 채점에는 사람이 검토한 기준 답안만 쓴다.

## Scoring criteria

| 기준 | 확인할 것 |
| --- | --- |
| 정확성 | 자격, 금액, 기한, 신청 경로처럼 상담자의 행동을 바꾸는 쟁점이 기준 답안과 맞는가 |
| 참조 | 필요한 근거를 찾았는가, 쓰지 않을 근거를 끌어오지 않았는가 |
| 오염 | 질문에 없는 사실, 다른 시점의 규정, 근거 밖의 내용이 답에 섞이지 않았는가 |
| 간결성 | 상담자가 이해할 수 있는가, 불필요하거나 중복된 내용이 없는가 |

- 결론에 필요한 사실이 빠진 사례는 확인 가능한 부분을 설명하고 필요한 사실을 되물었는지 본다.
- 범위 밖 질문에는 상담 범위 안내가 적절한지 본다. 근거가 부족한 경우에는 판단을 보류했는지, 답할 수 있는 질문까지 거절했는지도 확인한다.
- 같은 사례의 여러 표현은 한 건으로 센다.
- 문항, 기준 답안, 제품 버전은 결과를 보기 전에 정한다.
- 개발에 쓴 문항의 결과는 그 문항에 한해 보고한다.
- 답이 갈린 사례만 골라 얻은 결과는 그 사례에 한해 보고한다. 전체 점수에는 사전에 정한 평가 대상 중 두 답이 일치한 사례도 포함한다.
- 자체 챗봇의 검색은 전달된 근거와 기준 답안의 조문을 대조해 평가한다. 외부 서비스는 공개된 답변과 인용에서 확인할 수 있는 항목만 비교한다.

## Commands

질문 파일은 UTF-8 JSONL이며 각 행에 `id`, `as_of`, `question`이 있다.

```sh
uv run python -X utf8 scripts/bench_qa.py preview docs/evaluation/1350/questions.jsonl docs/evaluation/trial-01 --context historical --ids case-1
uv run python -X utf8 scripts/bench_qa.py freeze docs/evaluation/trial-01 docs/evaluation/fixed.json --ids case-1
uv run python -X utf8 scripts/bench_qa.py message docs/evaluation/fixed.json case-1
uv run python -X utf8 scripts/bench_qa.py blind docs/evaluation/fixed.json docs/evaluation/responses.jsonl docs/evaluation/grading-01
```

| 명령 | 결과 |
| --- | --- |
| `preview` | 두 조건의 첫 응답과 재현에 필요한 기록 |
| `freeze` | 검토를 마친 문항의 고정된 입력과 응답 |
| `message` | AI 노동법 상담에 붙여 넣을 질문 |
| `blind` | 출처를 가린 응답 쌍(`answers.json`)과 별도 배정표(`key.json`) |

`preview`는 입력, 상담일, 모델 설정, 코드와 wiki의 식별 정보를 저장한다. vault를 사용한 응답에는 검색한 노트와 근거도 저장한다. 과거 상담일을 질문에 명시할 때는 `--context historical`을, 원래 질문을 그대로 보낼 때는 `--context live`를 쓴다.

`blind`에 제공하는 외부 응답 파일(`responses.jsonl`)에는 `id`, `sent`, `first_response`를 담는다.
